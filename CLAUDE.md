# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Про проєкт

Особистий однокористувацький PWA-словник грузинської: Flask + SQLite на ПК, телефон заходить по Wi-Fi і працює офлайн. Клієнт — чистий JS без фреймворку; збірки й лінтера немає.

`README.md` — живий дизайн-документ: там описано кожну фічу і чому вона зроблена саме так (багато рішень свідомо обмежені). Перед зміною поведінки прочитай відповідний пункт у розділі «Що вміє».

## Команди

```
pip install -r requirements.txt
python app.py                    # порт 5000; https, якщо є mkcert, інакше http
python tests/run_all.py          # усі тести, сервер має бути запущений
python tests/test_words_api.py   # один серверний тест
node tests/js/test_srs.js        # один клієнтський тест
```

Чату потрібен `ANTHROPIC_API_KEY` у `.env` (зразок — `.env.example`). Без ключа `POST /api/chat` повертає 503, решта застосунку працює.

## Тести

- Це звичайні скрипти з `assert`, не pytest: успіх = код виходу 0.
- Серверні тести б'ють у **живий сервер і реальну `dictionary.db`**. Тому тестові дані мають префікс (`test-api-`, `test-srs-`, ...) і прибираються в кінці — нові тести мусять робити так само.
- Адреса за замовчуванням — `https://127.0.0.1:5000`. Якщо сервер без mkcert працює на http, задай `DICTIONARY_URL=http://127.0.0.1:5000`.
- Сервер не потрібен для `tests/js/*`, `test_backup.py` і `test_duplicates.py` (ті два підміняють `DB_PATH` на тимчасову базу). `test_chat_tools.py` теж без сервера, але пише напряму в реальну `dictionary.db`. `run_all.py` вимагає сервер у будь-якому разі.
- Тести ніколи не викликають справжній Claude API (це платно): інструменти чату перевіряються прямим викликом `execute_*`.
- `tests/js/_harness.js` склеює `static/js/*.js` і виконує разом із кодом тесту в одному `eval`, тож тест бачить внутрішні функції застосунку напряму. DOM там фейковий: якщо код під час завантаження чіпає новий DOM API, допиши його у `fakeEl()`.

## Архітектура

**Синхронізація слів і SRS.** Клієнт тримає повну копію `words` і `reviews` у localStorage і рендерить з неї. `sync()` (`static/js/store.js`) шле на `POST /api/sync` лише несинхронізоване, а тоді повністю замінює локальний стан відповіддю сервера. Слова дедуплікуються за UUID, згенерованим на клієнті (`INSERT OR IGNORE`); оцінки — last-write-wins за `reviewed_at`.

**Логіка SRS живе лише на клієнті** (`static/js/srs.js`) — сервер тільки зберігає результат. Усі рішення «чи пишемо в SRS» проходять через `writesSrs(correct)`: практичні сесії («Ще раз провалені», тренування за тегом) навмисно не рухають розклад. Виняток — повторення нотаток: воно лише на сервері (`/api/notes/<id>/review`, `note_reviews`).

**Вправи на реченнях** (`static/js/sentences.js`) — теж практика без запису в SRS. Речення додаються лише через `POST /api/sentences` (`word_uuid`, `sentence` з одним `____`, `answer`, `translation`, необов'язковий `hint`), у застосунку форми немає. Клієнт отримує їх через `/api/sync`. Відповідь перевіряється точно, без прощення одруківок: одна літера тут часто і є закінченням.

**Офлайн.** Додавання слів, повторення й вправи на реченнях працюють офлайн. Редагування, видалення синхронізованих слів, імпорт, операції над тегами, чат і нотатки — лише онлайн. `static/sw.js` — network-first з таймаутом, `/api/` не кешує; при зміні `SHELL` чи логіки кешування піднімай версію в `CACHE`.

**Чат** (`server/chat.py`). `POST /api/chat` запускає `_run_chat_generation` у фоновому потоці, а HTTP-відповідь лише читає з черги, тому генерація завершується, навіть якщо клієнт відключився. Звідси три вимоги:
- `threaded=True` в `app.run()` обов'язковий;
- `_chat_lock` пропускає одну генерацію за раз (інакше 409);
- у фоновому потоці `get_db()` недоступний — потрібне окреме `sqlite3.connect(DB_PATH)`.

Системний промпт збирається з бази на кожне повідомлення (`build_tutor_system`). Збої пишуться в `chat_errors.log`. Після відповіді клієнт викликає `sync()`, щоб підтягнути слова, додані інструментами.

**Новий інструмент чату** — це схема `*_TOOL` + `execute_*(conn, tool_input)`, зареєстровані в `CHAT_TOOLS` і `CHAT_TOOL_EXECUTORS`, плюс гілка в `_tool_call_summary`. Якщо інструмент шукає наявний запис — ще й `TOOL_LOOKUP_KEY` у `static/js/chat.js`. Executor приймає `conn`, щоб його можна було тестувати без API і перевикористовувати в HTTP-маршрутах (`POST`/`PATCH /api/notes`).

## Неочевидні інваріанти

- **Порядок скриптів.** `static/js/*.js` — не модулі, а спільна глобальна область; пізніші файли викликають функції попередніх уже під час завантаження. Порядок `<script src>` у `templates/index.html` має збігатися з `APP_FILES` у `tests/js/_harness.js`. Новий файл додавай в обидва місця.
- **Продубльована логіка, міняти разом:** `normalize_tags`/`RESERVED_TAGS` (`server/db.py` і `static/js/store.js`), інтервали `NOTE_INTERVALS` (`server/chat.py`) і `INTERVALS` (`static/js/srs.js`), `NETWORK_TIMEOUT_MS` (`static/sw.js` і `static/js/store.js`).
- **Теги** зберігаються рядком `"а, б"`. Порівнювати лише по токену, не по підрядку: SQL `LIKE` — тільки попередній відбір. `LEECH_TAG` і `VERB_TAG` — віртуальні значення `activeTag` з пробілом на початку, щоб не збігтися зі справжнім тегом. Теги `дієслово:<форма>` згортаються в один чип.
- **`georgian` не унікальне** (омоніми): ідентичність слова — `uuid`. Пошук за написанням має відмовляти чи не вгадувати при кількох збігах, як `edit_word`, `retag_word` і CSV-імпорт.
- **Час** — UTC-рядки `YYYY-MM-DD HH:MM:SS`; `reviewed_at` порівнюється лексикографічно, тож формат на клієнті й сервері має збігатися. У локальний час переводимо лише при показі.
- **Міграції** — вручну в `init_db()` (`server/db.py`): `PRAGMA table_info` + `ALTER TABLE`, фреймворку немає.
- **CSV-експорт** робить клієнт (`static/js/csv.js`), а не `/export.csv`: звичайне посилання «виносить» зі standalone-PWA на iOS. Нове поле слова додавай і туди, і в `/api/sync`, `/api/import`, `word_dict`.
